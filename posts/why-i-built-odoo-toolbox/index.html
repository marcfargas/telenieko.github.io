Why I Built odoo-toolbox

I pointed Claude at Odoo's docs. It hallucinated methods, invented field names, and wrote code that didn't work. So I lent it a hand.

I run several companies on Odoo. Legal, accounting, property management — all of it flows through Odoo. Invoices, contracts, timesheets, CRM leads, accounting entries. Thousands of records, dozens of models, years of data.

When AI coding agents got good enough to write real code, the obvious move was: point the agent at Odoo and start asking questions. “How much did we invoice last quarter?” “What’s the average collection time for this client?” “Post a note on that CRM lead.”

It didn’t work.

The hallucination problem#

Here’s what happens when you ask Claude, GPT, or any frontier model to interact with Odoo’s XML-RPC API:

It makes things up.

Not random garbage — plausible-sounding things. Method names that look right but don’t exist. Field names that follow Odoo’s naming conventions but aren’t real. API patterns from older versions mixed with current ones. The model has absorbed enough Odoo knowledge from the internet to be dangerous, but not enough to be correct.

I’d ask it to read invoices and it would call account.invoice.search — a model that was renamed to account.move years ago. I’d ask for customer data and it would reference customer_id when the field is actually partner_id. It would construct domains using operators that don’t exist in Odoo’s filter syntax.

The output looked professional. It compiled. It even ran — right up until the Odoo server returned an error about a model or field that doesn’t exist.

Why the obvious solutions don’t work#

“Just give it the docs.” Which docs? There’s Odoo Community, Odoo Enterprise, and the OCA ecosystem — three overlapping codebases with different modules, different fields, sometimes different behavior for the same model. And that’s before you account for the fact that every Odoo instance is different. Your instance has custom modules, specific patches, configuration flags that change field visibility, installed OCA addons that extend core models. The “Odoo docs” don’t describe your Odoo — they describe a platonic ideal that doesn’t match any production system. Even if you could figure out which docs to feed the model, dump all of it into context and you’ve blown the window. Even with large contexts, the model drowns in irrelevant information about modules you don’t use and patterns that don’t apply.

“Use RAG.” Retrieval-Augmented Generation sounds perfect in theory. Embed the docs, retrieve relevant chunks, feed them to the model. In practice, it retrieves the wrong patterns. A question about account.move retrieves fragments about invoicing, billing, credit notes, and journal entries — all mixed together, with no coherent mental model of how they relate. The model gets confused, not enlightened.

“Fine-tune on Odoo code.” Ignoring the cost and maintenance burden, this still doesn’t solve the core problem: Odoo’s API has version-specific behavior, field-level quirks, and read/write asymmetries that only surface when you actually test against a running instance. A fine-tuned model confident in wrong patterns is worse than a base model that admits uncertainty.

The fundamental issue isn’t lack of knowledge. It’s lack of structured, validated knowledge.

The insight: progressive, tested modules#

The solution came from thinking about how a human Odoo developer learns. Nobody reads all 12,000 pages. You learn connection first, then how to query, then how to write, then domain-specific operations. Each layer builds on the previous one.

So I built that learning path — but for AI agents.

odoo-toolbox is a set of knowledge modules that teach an agent Odoo progressively:

  1. Connection — how to authenticate, manage sessions, handle the RPC protocol
  2. Domains — Odoo’s query filter syntax, operators, composition rules
  3. Field types — the type system, the critical read/write asymmetries (you read a Many2one as [id, name] but write it as just id)
  4. CRUD — create, read, update, delete with all the edge cases
  5. Search — search patterns, pagination, field selection
  6. Introspection — discover models and fields dynamically (so the agent doesn’t have to guess)
  7. Properties — user-defined dynamic fields, a common source of confusion
  8. Modules — module lifecycle, installation, dependency management

Then domain-specific modules on top: mail and chatter, accounting entries, timesheets, attendance, contracts.

The agent loads only what it needs. Asking about invoices? Load connection + domains + CRUD + accounting. Posting a chatter message? Load connection + mail. The context stays focused.

The part that actually matters: CI testing#

Here’s the thing that separates this from yet another documentation project.

Every code example in every module is extracted and run against a real Odoo instance in CI. Not mocked. Not simulated. A Docker container with Odoo Community, a test database, and actual RPC calls.

The validation loop is simple and brutal:

  1. Write a skill module with code examples
  2. CI extracts every code block
  3. Each one runs against the real Odoo instance
  4. If any example fails, the build fails

This means the documentation can’t rot. When Odoo’s behavior changes, the CI catches it. When I write an example with the wrong field name, the CI catches it. When I describe an API pattern that doesn’t actually work, the CI catches it.

125 commits over four weeks. Every one of them tested.

The other part that actually matters: introspection#

The skills teach an agent how Odoo works in general. But your Odoo instance isn’t general — it has custom models, OCA modules, configuration-specific fields, and behavior that no documentation covers.

That’s where @marcfargas/odoo-introspection comes in. It lets the agent ask your Odoo instance directly: what models exist here? What fields does this model have? What type is this field, what’s it related to, is it required?

The workflow looks like this:

  1. Agent connects to your Odoo instance using the connection skill
  2. Agent uses the introspector to discover what’s actually there — not what the docs say should be there, but what is there
  3. Agent explores field types, relation targets, required fields, computed fields
  4. Agent tests operations against the live instance
  5. Once something works, it gets written into a skill module — a tested reference that won’t hallucinate

This is the loop that closes the gap between generic documentation and your specific Odoo. The base skills teach the agent how to talk to Odoo. The introspector teaches it what your Odoo looks like. And the CI pipeline ensures that what worked yesterday still works today.

What it looks like in practice#

With odoo-toolbox loaded, an agent can answer questions it would otherwise hallucinate on:

“What fields does account.move have for invoice amounts?” — The agent uses the introspection module to discover fields dynamically, instead of guessing from training data.

“Search for all draft invoices from January” — The agent constructs a proper domain filter using the syntax it learned from the domains module, not an approximation from Stack Overflow fragments.

“Post a note on partner record 42” — The agent uses the mail/chatter module, which teaches the exact message_post method signature and its keyword arguments.

The difference isn’t subtle. Before: the agent writes code that looks right and fails at runtime. After: the agent writes code that works, because it learned from tested examples, not internet fragments.

The ecosystem#

The skills are one part. The toolbox also ships TypeScript packages that back them:

  • @marcfargas/odoo-client — A lightweight RPC client. Handles authentication, session management, the JSON-RPC protocol. No Odoo framework dependency.
  • @marcfargas/odoo-introspection — Schema discovery. Ask “what models exist?” and “what fields does this model have?” programmatically.
  • @marcfargas/create-odoo-skills — Scaffold your own skill project. Fork the structure, point it at your Odoo instance, test your own modules.

The skills themselves are CC0 — public domain. Use them, modify them, ship them in your product, I don’t care. The TypeScript code is LGPL-3.0.

Installing the skill is one command:

npx skills add marcfargas/odoo-toolbox

Who this is for#

Not everyone.

If you run a business on Odoo and work with AI coding agents — Claude Code, Cursor, pi, whatever — this gives your agent accurate, tested knowledge about how Odoo actually works. No hallucinations, no guessing, no “let me try this method and see if it exists.”

If you’re building AI tooling for Odoo — chatbots, automation, reporting — the TypeScript packages give you a clean foundation without pulling in Odoo’s entire framework.

If you don’t use Odoo, this is irrelevant. And that’s fine.
